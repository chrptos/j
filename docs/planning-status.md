# 要件・設計の状況

- 要件定義：性能学習に絞る方針を反映したレビュー用初版。完了ではない。
- 技術選定：ADR-0001に記録済み。
- 設計：未完了。API契約・DBスキーマ・トランザクション境界・実験環境の詳細を決める必要がある。
- 実装：要件と設計のレビュー後に着手する。
- 未追跡のflows.mdとnon-functional-requirements.mdは以前のEC案であり、現在の確定仕様として扱わない。

## 要件で先に決める項目

| 項目 | 決める内容 |
| --- | --- |
| 検索 | キーワードの一致方式、並び順、ページ件数の上限 |
| 減算 | 数量上限、要求識別子の範囲・保持期間、失敗結果の再送時の扱い |
| 負荷モデル | 同時利用者数・操作頻度・RPS・読み書き比率・データ分布 |
| 非機能目標 | p95・p99、成功率、復旧時間、試験時間、使用資源、費用上限 |
| 復旧 | API停止・DB遅延時に期待する結果、タイムアウトと再試行の条件 |

## 要件レビュー後の設計

- APIの入出力、エラー、要求識別子の契約を定義する。
- 商品・在庫・減算要求のテーブルと制約、初期インデックスを定義する。
- 在庫更新と要求結果の保存を一つのトランザクションにする方法を決める。
- 同じ要求の並行実行と、応答消失後の再送のシーケンスを整理する。
- API・DB・計測・負荷生成の構成と、資源制限を定義する。
- 各試験の条件、判定基準、DB整合性の検証方法を定義する。
- バージョンを固定し、起動・データ生成・試験の再現手順を決める。

## 完了の基準

- 要件：上記の条件と数値を合意し、判定可能な受入条件を記載する。
- 設計：合意した要件をAPI・DB・処理境界・試験方法へ対応付け、レビューする。
- 初期測定を根拠に見直す目標は、暫定値と見直し条件を明記する。
