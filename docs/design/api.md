# API設計

状態：レビュー用の提案 / 関連Issue：#13

## 1. 商品検索

### リクエスト

`GET /products`

| パラメータ | 内容 | 初期案 |
| --- | --- | --- |
| keyword | 商品名の部分一致 | 任意。未指定なら条件なし |
| categoryId | カテゴリID | 任意 |
| minPrice | 価格の下限 | 任意。境界を含む |
| maxPrice | 価格の上限 | 任意。境界を含む |
| sort | 並び順 | `id_asc`（標準）、`price_asc`、`price_desc` |
| limit | 取得件数 | 標準20、1〜100 |
| offset | 取得開始位置 | 標準0、0以上の整数 |

- 商品IDは昇順を基本とする。価格が同じ場合も商品IDの昇順で並べる。
- 初期版はOFFSET方式とし、カーソル方式を比較実験で追加する。
- 件数、ID、価格、offsetの型や範囲が不正な場合は400を返す。
- minPriceがmaxPriceを超える場合は400を返す。
- キーワードの大文字小文字、文字正規化、長さ上限は別途レビューで決める。

### レスポンス

- 成功：200。該当商品がない場合も空のitemsを返す。
- カテゴリが存在しない場合は、検索結果を空にする案。
- 総件数は初期レスポンスに含めず、次ページの有無を返す案。
- hasNextは指定件数より1件多く取得して判定する。

```json
{
  "items": [
    {"id": 1, "name": "商品A", "price": 1000, "categoryName": "カテゴリA"}
  ],
  "limit": 20,
  "offset": 0,
  "hasNext": false
}
```

## 2. 在庫減算

### リクエスト

`POST /products/{productId}/stock/decrements`

```json
{"quantity": 1}
```

- 1リクエストで1商品を指定する。
- productIdとquantityは正の整数とする。
- quantityの最大値と数値の保存型はDB設計で決める。
- 各リクエストを独立した減算として扱う。

### レスポンス

| 状況 | ステータス | コード |
| --- | --- | --- |
| 減算成功 | 200 | — |
| 入力不正 | 400 | INVALID_ARGUMENT |
| 商品なし | 404 | PRODUCT_NOT_FOUND |
| 在庫不足 | 409 | INSUFFICIENT_STOCK |
| 一時的なDB障害 | 503 | 第3章の分類に従う |
| 予期しない障害 | 500 | INTERNAL_ERROR |

```json
{"productId": 1, "remainingStock": 9}
```

- remainingStockは、このリクエストの更新時点の在庫数を返す。別のリクエストでその後に変わる可能性がある。
- 応答が届かなくても減算が成立している場合がある。再送すると別の減算になるため、負荷試験では自動再試行を行わない。
- 障害試験の整合性確認では、応答成功件数だけでなくDBの更新結果を確認する。確認方法は試験設計で決める。

## 3. エラー設計

以下はレビュー用の提案。HTTPの分類とアプリケーションのコードを揃え、負荷試験でも結果を分ける。

### レスポンス形式

- RFC 9457のProblem Detailsを使い、Content-Typeを`application/problem+json`にする。
- typeはエラー種類を表す固定URIとする。例の`urn:j:problem:insufficient-stock`は識別子であり、取得用URLではない。
- statusは実際のHTTPステータスと一致させる。
- codeは集計用の固定コード、detailは利用者向けの説明、traceIdはログとの照合用とする。
- instanceは発生したエラーを識別するURIとし、traceIdから生成する。
- 入力不正ではerrorsにfield・code・messageを返す。SQL・接続先・スタックトレース・入力値は返さない。

```json
{
  "type": "urn:j:problem:insufficient-stock",
  "title": "在庫不足",
  "status": 409,
  "detail": "指定された数量の在庫がありません",
  "instance": "urn:uuid:ca326a98-8885-4b23-a456-7dd3ab5c27c4",
  "code": "INSUFFICIENT_STOCK",
  "traceId": "ca326a98-8885-4b23-a456-7dd3ab5c27c4"
}
```

### 分類

| 状況 | HTTP | code | 試験時の分類 |
| --- | --- | --- | --- |
| JSON・型・範囲・検索条件が不正 | 400 | INVALID_ARGUMENT | 入力不正 |
| 対象商品なし | 404 | PRODUCT_NOT_FOUND | 業務上の拒否 |
| URLなし | 404 | ENDPOINT_NOT_FOUND | 入力不正 |
| 許可されないHTTPメソッド | 405 | METHOD_NOT_ALLOWED | 入力不正 |
| 未対応のContent-Type | 415 | UNSUPPORTED_MEDIA_TYPE | 入力不正 |
| 在庫不足 | 409 | INSUFFICIENT_STOCK | 業務上の拒否 |
| 利用者単位のレート制限（導入時） | 429 | RATE_LIMITED | 負荷制御による拒否 |
| サービス全体の同時実行上限（導入時） | 503 | SERVICE_OVERLOADED | システム側の拒否 |
| DB接続不可・プール取得タイムアウト | 503 | DATABASE_UNAVAILABLE | システム障害 |
| DBクエリ・ロック待ちタイムアウト | 503 | DATABASE_TIMEOUT | システム障害 |
| デッドロック・直列化失敗で処理を中断 | 503 | TRANSACTION_ABORTED | システム障害 |
| 予期しない例外・データ整合性違反 | 500 | INTERNAL_ERROR | システム障害 |

- 入力検証後に在庫更新を行う。障害を在庫不足として扱わない。
- 商品が存在するのに在庫行が欠けている場合は整合性違反とする。
- 405ではAllowヘッダーを返す。
- 429・過負荷の503では、待機時間を設定できる場合にRetry-Afterを返す。初期版でレート制限・負荷制御を実装するかは別の設計判断とする。
- アプリが返せるエラーは共通形式にする。接続断・プロキシ側エラー・強制終了では形式や応答を保証できない。
- DBタイムアウトの具体的な時間と例外の対応はDB設計で固定する。

### 再試行と減算結果

- 検索は副作用がないため、一時障害では回数上限付きの待機を伴う再試行を検討できる。基準測定では再試行なしにする。
- 在庫減算は再送対応がないため、503・タイムアウト・接続断でも自動再試行しない。Retry-Afterも再送の安全性を示すものではない。
- コミット時の接続断などでは、更新が成立したか断定できない。エラー応答や応答欠落を、未更新の証拠にしない。
- 競合・障害試験ではDBの最終在庫と成立した更新を照合する。計測方法は試験設計で決める。

### 実装方針・ログ

- 入力不正と業務上の拒否は専用の例外・結果型で表す。
- Spring MVCの共通例外ハンドラーでProblem Detailsへ変換する。フレームワーク由来の400・404・405・415も揃える。
- DB例外は原因を分類し、判定できないものは500にする。
- ログにtraceId、API、HTTPステータス、code、処理時間を記録する。
- 想定内の拒否はスタックトレースを付けず、障害は原因を記録する。負荷試験でログが性能を歪めないよう、出力量も固定する。
- リクエスト全体や接続情報はログへ出さない。
- HTTPステータスとcodeで集計する。traceIdはメトリクスのラベルに使わない。

### 検証項目

- 入力不正・在庫不足・商品なしのHTTPとcodeが一致する。
- DB停止・プール枯渇・ロック待ちで、業務上の拒否とは別の結果になる。
- エラー形式、statusとHTTPの一致、traceIdとログの対応を確認する。
- エラー応答に内部情報が含まれない。
- 在庫不足・入力不正で在庫が変わらず、競合でも在庫が負にならない。
- 応答消失時の成立結果をDB側で検証できる。
